CONTEXT:
User requested ability to lock selected particle in place, like a rock in the
fluid. The particle should be selectable, scalable, but immovable - acting as
a fixed obstacle that other particles flow around.

APPROACH:
Rather than skip physics entirely for the selected particle, we let it
participate in force calculations (so other particles interact with it
properly), but we lock its position and zero its velocity after integration.

This ensures:
  1. Other particles "see" the selected particle and collide with it
  2. SPH forces from selected particle affect neighbors
  3. Selected particle doesn't move (position locked)
  4. No velocity accumulation (zeroed each frame)

IMPLEMENTATION DETAILS:

1. C++ Structure Change (utilities.hpp):
   Added field to ComputePushConstants:
     uint32_t selectedParticleIndex;  // UINT32_MAX if none selected

   This matches the graphics push constants pattern.

2. Compute Shader (create-compute-pipeline.hpp):

   Early in main() after loading particle:
     vec3 savedPosition = p.position.xyz;
     bool isSelectedParticle = (index == pushConstants.selectedParticleIndex);

   After position integration (line 257-258):
     // Lock selected particle in place (acts like a rock in the fluid)
     if (isSelectedParticle) {
         p.position.xyz = savedPosition;  // Restore original position
         p.velocity.xyz = vec3(0.0);      // Zero velocity (no movement)
     }

   Reasoning: We save position BEFORE any physics calculations, then restore
   it AFTER integration. This means the particle participates in density,
   pressure, and collision calculations (other particles push against it), but
   ultimately stays in place.

3. Push Constants (main.cpp):
   Line 386:
     computePushConstants.selectedParticleIndex = 
       selectedParticleIndex >= 0 ? (uint32_t)selectedParticleIndex : UINT32_MAX;

   Uses same pattern as graphics pipeline - UINT32_MAX means no selection.

DECISIONS MADE:

Decision: Let particle participate in physics before locking
Reasoning: If we skip physics entirely, other particles won't interact with it
properly. By calculating forces but locking position/velocity, we get proper
interaction without movement.

Decision: Save position early, restore late
Reasoning: Ensures all physics calculations use correct (locked) position.
Restore happens after integration, boundaries, and all other updates.

Decision: Zero velocity instead of preserving it
Reasoning: Prevents velocity accumulation from forces. Selected particle truly
acts as a stationary object, not a "heavy" object that slowly drifts.

Decision: Use UINT32_MAX as "no selection" sentinel
Reasoning: Matches existing pattern in graphics pipeline. -1 in int32_t is
UINT32_MAX in uint32_t, so conversion is safe.

CONTEXT FOR FUTURE SESSIONS:
The lock behavior is implemented at the physics integration stage, not by
skipping physics. This is important if we add more complex interactions later

counter should never increment.
