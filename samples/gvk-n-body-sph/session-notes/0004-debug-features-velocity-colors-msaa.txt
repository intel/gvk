================================================================================
TECHNICAL CHALLENGES
================================================================================

ISSUE 1: Push Constants Alignment Mismatch
Problem: GUI checkboxes had no effect (velocity colors, hard edges)
Cause: GLSL std140 layout aligns vec3 to 16 bytes, C++ glm::vec3 is 12 bytes
Solution: Added alignas(16) to C++ vec3 fields, updated push constant range to 112 bytes
Files: main.cpp, create-graphics-pipeline.hpp

ISSUE 2: Runtime MSAA Toggling Complexity
Attempted: Dynamic WSI context/pipeline recreation when checkbox toggled
Problems: 
  - Flickering/corruption when recreating during frame
  - Attempted deferred recreation after queue_present
  - Still unstable and complex
Decision: BACKED OUT all runtime MSAA toggling code
Result: MSAA now startup-only, simpler and stable

ISSUE 3: MSAA Validation Error on Startup
Error: "rasterizationSamples (1) does not match RenderPass samples (4)"
Cause: Graphics pipeline only checked VkRenderPassCreateInfo (Vulkan 1.1)
       On Vulkan 1.2+, WSI creates VkRenderPassCreateInfo2 instead
       Pipeline got empty struct ? default VK_SAMPLE_COUNT_1_BIT
Solution: Check both renderPassCreateInfo and renderPassCreateInfo2
Files: create-graphics-pipeline.hpp

================================================================================
LESSONS LEARNED
================================================================================

1. GLSL std140 Alignment Matters
   - vec3 in GLSL is 16-byte aligned (padded like vec4)
   - Must use alignas(16) in C++ for matching structs
   - Push constant size must account for padding

2. GVK Handles Multiple Vulkan Versions
   - Check both VkRenderPassCreateInfo and VkRenderPassCreateInfo2
   - Pattern used throughout GVK codebase (gui/renderer.cpp, wsi-context.cpp)
   - Always check sType before accessing struct fields

3. Runtime Resource Recreation is Tricky
   - WSI context recreation requires careful synchronization
   - Must wait for GPU idle + recreate dependent resources
   - Deferred recreation (flag ? recreate after frame) is cleaner
   - Sometimes "startup only" is the right answer for complexity/benefit

4. Code Smells to Watch For
   - Tracking state with "previous" variables across frames
   - Checking for changes every frame instead of on-event
   - Better: Use ImGui return values, flag events, handle once
